## 2. Core Architectural Patterns

The AMAS Farm backend adheres to a strict 4-tier architecture:

1. **Models (SQLAlchemy):** Defines the database schema and relationships.
2. **Schemas (Pydantic):** Validates incoming and outgoing API payloads. Always split into `Create`, `Update`, and `Response` definitions.
3. **Repository (`*Repo.py`):** The *only* layer allowed to execute raw database queries. Methods here should be static.
4. **Service (`*Service.py`):** Holds the business logic. It orchestrates Repository calls, calculates derived values (like net salary or remaining balance), enforces rules, and triggers database commits/rollbacks.

### The Golden Rule of Database Transactions

When a single user action requires modifying multiple tables (e.g., recording a payroll and inserting a payment, which then creates a ledger transaction), **the entire operation must be atomic**. 

**Wrong Approach (Repo-Level Commits):**
```python
# If the payment insert fails, the payroll is still saved! This causes data corruption.
await PayrollRepo.create(db, payroll) 
await PayrollPaymentRepo.create(db, payment) 
```

**Right Approach (Service-Layer Orchestration):**
Always pass `commit=False` to the repository methods so they merely `db.add()` or `db.flush()`. The Service layer is responsible for the final `await db.commit()`.

```python
# Service Layer Example
try:
    # 1. Create the parent record, flushing but NOT committing yet
    created_payroll = await PayrollRepo.create(db, new_payroll, commit=False)

    # 2. Add the payment record
    await PayrollPaymentRepo.create(db, payment) # Inside Repo: db.add(payment)

    # 3. Add the ledger transaction
    db.add(financial_transaction)

    # 4. Commit everything together atomically
    await db.commit()
    await db.refresh(payment)
    return payment

except Exception as e:
    # 5. If ANY step fails, roll back everything to keep the DB clean
    await db.rollback()
    raise HTTPException(status_code=500, detail=f"Transaction failed: {str(e)}")
```

## 3. Navigating Alembic Migrations

Autogenerated migrations are dangerous if you have existing data. 

When you add a new `NOT NULL` column (like `amount_paid` or `payment_status`), Alembic will generate an `add_column` instruction with `nullable=False`. **If you run this against a database with existing rows, PostgreSQL will throw an error** because the existing rows won't have a value for the new column.

**How to safely patch an Alembic migration:**

1. Change the autogenerated `add_column` to `nullable=True`.
2. Inject a raw SQL `op.execute(...)` to backfill existing rows with a default value.
3. Use `op.alter_column` to flip the column back to `nullable=False`.

**Example:**
```python
def upgrade() -> None:
    # 1. Add as nullable
    op.add_column('assets', sa.Column('amount_paid', sa.Numeric(precision=15, scale=2), nullable=True))
    
    # 2. Backfill existing data
    op.execute("UPDATE assets SET amount_paid = 0.00")
    
    # 3. Enforce the NOT NULL constraint
    op.alter_column('assets', 'amount_paid', existing_type=sa.Numeric(precision=15, scale=2), nullable=False)
```

## 4. Testing Your Logic (The Proof)

Do not assume your code works just because it looks correct. You must prove it.

For backend logic that involves complex state changes, write standalone async Python test scripts. These scripts should directly invoke the `Service` classes using a raw `AsyncSession`.

**Testing Checklist:**
1. **Dependency Mocking:** Your script will need parent records (like an Employee, a User, or an Account). Write defensive SQL to `SELECT` an existing record, or `INSERT` a dummy record if none exist.
2. **Test the Happy Path:** Does the record create successfully? Are all calculated fields accurate?
3. **Test the Edge Cases:** 
    - What happens if the payment amount exceeds the balance? (Should raise `HTTPException 400`)
    - What happens if a foreign key is missing? (Should rollback safely).
4. **Inspect the State:** Fetch the record *after* the operation and assert that statuses (e.g., `UNPAID` -> `PARTIAL` -> `PAID`) transitioned correctly.

### Dealing with SQLAlchemy Quirks in Tests

When you `db.commit()`, SQLAlchemy expires all objects. If you try to access an attribute on the object afterward (like `payment.id` or `payment.reference`), it will try to lazy-load it, which will fail asynchronously with a `MissingGreenlet` error.

**Always `db.refresh(obj)` immediately after `db.commit()` if you need to read its properties.**

## 5. Summary of Best Practices for Future AI Models

If you are an AI model assigned a new task on this project, follow this exact workflow:

1. **Read and Research:** Do a `grep_search` or `find_by_name` to locate all related models, repos, services, and schemas.
2. **Draft a Plan:** Think through the exact sequence of files you need to modify. 
3. **Implement Models and Schemas:** Start from the bottom layer (data definitions).
4. **Implement Repositories:** Keep them simple. Support `commit=False`.
5. **Implement Services:** This is your command center. Handle atomic transactions here.
6. **Implement Routers:** Expose the logic via FastAPI.
7. **Migrate the Database:** Run `alembic revision --autogenerate`. *Manually inspect and patch the generated file for `NOT NULL` constraints.* Run the upgrade.
8. **Test Rigorously:** Write a script, execute it against the Docker container, and verify the console output.

*By adhering strictly to these principles, you will write bulletproof, enterprise-grade code that never corrupts the database.*
